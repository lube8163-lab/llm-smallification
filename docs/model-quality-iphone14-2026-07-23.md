# Gemma 4 12B Core ML 実機品質評価（2026-07-23）

## 条件

- iPhone 14（iPhone14,7 / iOS 26.5.2）
- target: `pal4_g16`、endpoint: `pal4_g16`
- greedy decode、mixed MTPドラフタ、adaptive top-3 tree有効
- テキスト8種、実PNG、実WAVに加え、失敗項目の短答化・上限拡張・target単独対照を実施
- RunPodは使用していない

これは20問の小規模な診断セットであり、MMLU等の統計的スコアではない。現在の
Core MLモデルが実際にどのように答えるか、品質低下が投機デコード由来か、回答速度と
安定性がどうかを確認する目的で実施した。

## 主評価

`tok/s` はAPIリクエスト全体のend-to-end値。括弧内は端末の生成レポートに記録された
モデル生成区間の値。

| 分類 | 質問の要点 | 回答 | 判定 | tok/s |
|---|---|---|---|---:|
| 常識 | 日本の首都 | `東京` | 正解 | 0.064（0.098） |
| 算術 | 17×23 | `419` | 不正解 | 0.114（0.166） |
| 論理 | 鳥→動物、ペンギン→鳥 | `はい`＋正しい理由 | 正解だが20 tokenで文末切れ | 0.197（0.221） |
| 指示追従 | 3色をJSON配列だけで出力 | `["赤", "青", "緑"]` | 正解 | 0.246（0.342） |
| Swift | `square(_:)`を実装 | 完全な`n * n`関数 | 正解、Macでcompile/run成功 | 0.423（0.534） |
| 抽象 | 自由と責任の両立条件2点 | 1点目の途中まで | 未完結 | 0.277（0.307） |
| 幻覚耐性 | 架空理論の発表年 | `森崎レオンという学`＋特殊token/0反復 | 不合格 | 0.199（0.251） |
| 翻訳 | battery切れで実験失敗 | 前置きだけで24 token消費 | 不合格 | 0.281（0.324） |
| 画像 | RunPod画面のサービス・状態・接続 | `runpod.io`まで回答 | 部分正解、32 tokenで打切り | 0.239（0.264） |
| 音声 | “What is two plus two?” | `4` | 正解 | 0.229（0.232） |

主評価の合計は161 token / 664.22秒で、end-to-end **0.242 tok/s**、
モデル生成区間 **0.287 tok/s**。テキスト8問だけではそれぞれ
**0.243 tok/s**、**0.294 tok/s**だった。

短答は固定のプリフィル・セットアップ時間を少数tokenで償却できないため、見かけの
tok/sが特に低い。長く、かつMTPの予測が当たりやすいコード回答は0.534 tok/sまで上がった。

## 追試で分かったこと

### 算術はモデル出力そのものの弱点

- 同じ17×23を再実行しても`419`で、greedy出力は再現した。
- 途中計算を32 tokenに広げると
  `17 × 23 = 17 × (20 + 3) = 340 + 51`までは正しいが、最終結果を`421`とした。
- 投機デコードを完全に無効化したtarget単独でも`419`だった。

したがって、これは投機デコードの誤受理ではなく現在のtarget出力の問題である。

### 短答指定で改善する項目が多い

| 項目 | 短答追試の回答 | 判定 |
|---|---|---|
| 抽象 | `1:自己決定の主体性` / `2:結果への責任` | 2点を区別して完結 |
| 幻覚耐性 | `確認できない` | 合格 |
| 翻訳 | `電池切れのため、実験は失敗しました。` | 合格 |
| 画像のPod状態 | `動作中` | 合格 |
| 画像の接続方法 | `HTTP services / SSH / SSH over exposed TCP` | 画面どおり3項目を認識 |

現在のモデルは、能力が完全に失われているというより、自由回答で前置きや箇条書きを
始めると、32 token程度の上限では本題前に打ち切られやすい。実用UIでは質問を短答・
JSON形式へ寄せるか、上限を増やしてEOSまで生成する必要がある。

## 画像・音声

- 実PNGから`runpod.io`、Podが`動作中`、`HTTP services`、`SSH`、
  `SSH over exposed TCP`を読み取れた。画像理解は機能している。
- 画像接続回答の32 token再試験は27 tokenで自然終了し、モデル生成区間
  **0.448 tok/s**。warm decodeは1.82秒/token（**0.549 tok/s**）、
  MTP acceptance 0.667、2.89 tokens/sweep、peak 781.8 MBだった。
- 0.96秒、16 kHz / mono / Int16の実WAVに含めた
  “What is two plus two?”へ`4`と回答した。音声理解も短い明瞭な入力では機能した。
- 音声回答は0.232 tok/s、peak 581.0 MB。

## 安定性・出力健全性

- 主セッションはウォームアップを含む20リクエストをクラッシュ・OOM・API失敗なしで完走。
- 初回verifyコンパイル時の観測peakは808.4 MB。終了前のプロセスメモリは157.0 MB、
  available memoryは3,939 MBだった。
- 幻覚耐性の初回回答でmultimodal制御token `258882`の後にpad token `0`が4回続いた。
  反復停止は働いたが、制御tokenをLM headでmaskし、padを即時停止対象にする改善余地がある。
- 投機あり・なしで算術の出力が一致したため、投機デコードがtargetのgreedy品質を
  変えていないことも対照試験で確認した。

## 結論

現在のCore MLモデルは、常識短答、単純論理、構造化出力、簡単なSwift生成、
対象を絞った画像・音声理解では実用的な回答を返した。一方で、算術は明確に弱く、
自由回答は冗長な構成と短い生成上限によって未完結になりやすい。幻覚耐性もプロンプト形式に
敏感で、制御token流出というランタイム側の改善点も見つかった。

今回の結果だけでは、これらが元のGemma 4 12Bの能力限界か、pal4量子化・Core ML変換で
生じた劣化かは分離できない。次に品質を厳密に判断する場合は、同じ問題とgreedy設定を
bf16/fp16参照モデルで実行し、token ID単位で比較するのが最優先になる。この参照実行は
RunPod等のGPU環境を使う価値があるが、現在のiPhone実装の利用・再試験にはRunPodは不要。
