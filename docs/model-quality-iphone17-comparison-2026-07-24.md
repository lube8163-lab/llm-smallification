# Gemma 4 12B Core ML iPhone 17品質・速度比較（2026-07-24）

## 結論

iPhone 14と同じ9問を同じプロンプト、token上限、greedy decode、投機デコード設定で
iPhone 17に実行したところ、**回答本文と出力token IDは9/9で完全一致**した。
端末変更によってモデル品質が変わった形跡はない。

一方、同条件の速度はiPhone 17の方が遅く、end-to-endで8.3%、端末が記録した
モデル生成区間で14.5%低かった。また、出力上限を64〜96 tokenへ広げた長文試験では、
回答品質が改善する項目がある一方、Core ML推論が停止したまま戻らない事象が複数回発生した。
現時点のiPhone 17では、速度よりもランタイム安定性が先に解決すべき問題である。

## 試験条件

- iPhone 14: iPhone14,7 / iOS 26.5.2
- iPhone 17: iPhone18,3 / iOS 26.4.2
- target / endpoint: `pal4_g16`
- greedy decode、mixed MTPドラフタ、adaptive top-3 tree有効
- 実PNGと16 kHz / mono / Int16の実WAVを使用
- iPhone 17の長文試験は64〜96出力token
- RunPodは使用していない

これは少数の診断問題による実機評価であり、MMLU等の統計的ベンチマークではない。
また、端末間でiOS版が揃っていないため、SoCだけの厳密な性能比較ではない。

## iPhone 14との同条件比較

音声を除くテキスト8問と画像1問の集計。音声はiPhone 17の初回フルアプリで
端末ストレージ不足が発生したため、後述の最小アプリで別に比較した。

| 端末 | 完了数 | 出力token | API全体 | API tok/s | モデル生成区間 | モデル tok/s |
|---|---:|---:|---:|---:|---:|---:|
| iPhone 14 | 9/9 | 159 | 655.50秒 | 0.243 | 553.15秒 | 0.287 |
| iPhone 17 | 9/9 | 159 | 714.92秒 | 0.222 | 646.99秒 | 0.246 |
| iPhone 17の差 | — | — | +9.1% | **-8.3%** | +17.0% | **-14.5%** |

回答の傾向もiPhone 14と同じだった。

| 分類 | 同一回答の判定 |
|---|---|
| 常識 | `東京`で正解 |
| 算術 | `419`で同じ誤答 |
| 論理 | 結論と理由は正しいが20 tokenで文末切れ |
| JSON | 指示どおりの配列で正解 |
| Swift | 完全な二乗関数で正解 |
| 抽象 | 1点目の途中で32 token上限 |
| 幻覚耐性 | 特殊token流出後に打切り、不合格 |
| 翻訳 | 前置きで24 tokenを使い切り、不合格 |
| 画像 | RunPodを認識したが32 tokenで途中終了 |

特に、誤答を含めてtoken IDまで一致していることから、投機デコードや端末差による
greedy出力の変化は今回の比較では観測されなかった。

## 出力上限を広げた品質試験

完了した7問は合計401 token / 1,179.60秒で、end-to-end **0.340 tok/s**、
モデル生成区間は1,073.15秒、**0.374 tok/s**だった。短答試験よりtok/sが高いのは、
固定のプリフィル・セットアップ時間を長い出力で償却できるためである。

| 分類 | 上限 | 結果 | 品質判定 |
|---|---:|---|---|
| 算術 | 64 | 分配法を説明したが計算途中で終了 | 不合格。token増加だけでは解決せず |
| 論理 | 64 | `結論：導けません` | 結論は正解、理由は特殊tokenで途中終了 |
| JSON | 64 | 指定されたオブジェクトを出力 | 構文・値とも完全に正解 |
| Swift二分探索 | 96 | 探索処理の前半まで生成 | 方針は正しいが関数が未完結でcompile不可 |
| 抽象 | 96 | 危害禁止原則を説明し、第2原則を開始 | 内容は妥当だが未完結 |
| 幻覚耐性 | 64 | 架空の論文で実在しないと明記 | 合格。ただしオフラインなのに「調べた」という表現あり |
| 翻訳 | 64 | 自然で完全な一文を32 tokenで終了 | 人手判定で合格 |
| 画像詳細 | 96 | 応答生成中にCore ML推論が停止 | 評価不能 |

上限拡張は翻訳、幻覚耐性、JSON、抽象説明の情報量には有効だった。しかし、
冗長な算術説明やコード生成では96 tokenでも不足し、単純に上限だけを増やすと
待ち時間と停止リスクが増える。タスク別の出力形式指定と上限設定が必要である。

## 画像・音声

### 画像

- 32 token試験では実PNGからRunPod画面を認識し、画像入力自体は動作した。
- iPhone 14の短答追試ではPodの稼働状態と3種の接続方法まで正しく回答できている。
- iPhone 17の96 token詳細回答は、投機デコード7巡目のverify中に停止し、回答を保存できなかった。

したがって、画像理解能力の欠落ではなく、iPhone 17上の長いマルチモーダル生成の
安定性が未確認部分として残った。

### 音声

同じ実WAVの “What is two plus two?” に、両端末とも `4`と回答した。

| 条件 | API時間 / tok/s | モデル生成時間 / tok/s | 結果 |
|---|---:|---:|---|
| iPhone 14、主セッション内 | 8.73秒 / 0.229 | 8.64秒 / 0.232 | 正解 |
| iPhone 17、最小アプリ初回 | 126.01秒 / 0.016 | 45.41秒 / 0.044 | 正解、初回compile込み |
| iPhone 17、compile cache後に新規起動 | 11.73秒 / 0.170 | 4.80秒 / 0.417 | 正解 |
| iPhone 17、同一プロセスで2回目 | — | — | 推論停止 |

iPhone 17はcache後のモデル生成区間だけを見ると速いが、起動・ロードを含むAPI全体では
iPhone 14より遅かった。アプリ構成、cache状態、OS版が異なるため、この1問だけで
音声性能の優劣は断定しない。

## 安定性とストレージ

- 190個のモデルを含む約24GBのフルアプリでは、テキスト・画像実行後の音声モデルcompile時に
  iPhoneの空き容量が不足した。
- 再変換は行わず、既存成果物からテキスト＋画像約12GB、音声約6.1GBの最小アプリを作り分けた。
- 最小化後はストレージエラーは解消した。
- 長文テキストを同一プロセスで連続実行すると、5問目のverify中に停止した。
- 新規プロセスで抽象問題を再実行すると完了した。
- 画像96 tokenは新規プロセスでもverify中に停止した。
- 音声は初回成功後、同一プロセスの2回目でdecoder途中に停止した。新規起動では再び成功した。
- iPhone 14の主セッションは20リクエストをクラッシュ・停止なしで完走している。

停止時はCPU使用率が0%となり、タイムアウトを待ってもCore ML呼び出しが返らなかった。
発生層が毎回異なり、プロセス再起動で一部が回復するため、モデル回答品質より
Core ML / ANEランタイム、compile cache、モデル常駐再利用の組み合わせが原因である
可能性が高い。ただし、iOS版を揃えた再試験までは断定しない。

## 推奨する次の対応

1. iPhone 17をiPhone 14と同じiOS 26.5.2へ揃えて再測定する。現状の速度差と停止を
   ハード差として扱わない。
2. 当面は長文・画像・音声を別プロセスまたは少数リクエスト単位で実行し、watchdogで
   無応答時にプロセスを再起動できる構成にする。
3. 出力上限は一律に増やさず、短答・JSONは32〜64、コード・抽象説明は安定性修正後に
   128〜160を候補とする。回答形式と文字数もプロンプトで強く制約する。
4. 算術はtoken増加で直らなかったため、電卓ツールや決定的な計算処理へ委譲する。
5. 特殊tokenとpad tokenを出力候補からmaskし、早期停止条件を強化する。
6. 製品アプリでは全モデルを常時同梱せず、テキスト、画像、音声をオンデマンド資源に分ける。
